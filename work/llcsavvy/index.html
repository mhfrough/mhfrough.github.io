    Every wizard screen posts to the API, so the order reopens on the step the customer left.

  • 02

    Two currencies

    Prices stay in dollars, as the state fees are. Each company’s subtotal and the total add their rupee amount at the day’s rate.

  • 03

    A code swaps in its own price for each product it covers. The server answers with the new lines, so the cart never does the discount maths itself.

Decisions and what I’d change

A sister product on a copied codebase, a new market, and money that had to cross a currency on the way in.

  1. 01

    Start from the sister

    Copying Finclore gave LLC SAVVY a working wizard, portal and back office on day one. The time went into what its market needed: the money and the content.

  2. 02

    Dollars first, rupees beside

    State fees are set in dollars, so prices stay in dollars and the rupee amount sits under each subtotal, with the rate and its source. Customers see what leaves their account before they reach the bank screen.

  3. 03

    Let the bank confirm

    Receipts meant a person checked every payment. The direct debit validates the customer with their bank and asks for an OTP only when the bank does, so an order reaches the queue without anyone checking a picture.

  4. 04

    Promo maths on the server

    The cart sends only the code and gets back repriced lines. One place decides what a code is worth, and its dates are checked where its prices live.

  5. 05

    One codebase, not two

    Two copies meant every shared fix landed twice, and a few shared illustrations still carried the sister’s name. Today I’d run both brands from one codebase with a theme and a config per brand.

  6. 06

    Payments behind one interface

    The gateway arrived as a new branch of the payment screen beside the transfer flow. Today I’d put each method behind one interface, so a new one is a new class, not a new screen.

A product that has to work in two currencies?

Checkouts, local payment methods and back offices that agree with their API.
