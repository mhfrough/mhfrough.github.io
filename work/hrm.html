One record, end to end

In most small companies here, attendance, leave and payroll live in three spreadsheets that someone stitches together every month end. HRM Suite keeps one employee record that every module reads and writes.

  1. 1Hired on the web
  2. 2Checks in on the phone
  3. 3Attendance entry
  4. 4Payroll input
  5. 5Payslip in the phone inbox
  6. 6Posted to the books

  • Employees

    Employee master, org chart and structure, change requests on whitelisted fields.

  • Attendance

    Geo-fenced phone punches, shifts, rosters, punch import and regularization.

  • Leave

    Policies, balances, a team calendar and holidays, routed to approvals.

  • Approvals

    One approval centre with maker-checker, SLAs, risk and delegation.

  • Payroll

    Guided runs with proration, loan recovery, salary tax slabs and payslips.

  • Loans and benefits

    Advances recovered through payroll, claims reimbursed through it too.

  • Tax and insurance

    Filer and non-filer withholding, filings due, policies and premiums.

  • Self service

    Clock in, leave, payslips, claims and requests for every employee.

  • Accounts

    Double-entry books that payroll, claims and loans post to on their own.

  • Inbox and chat

    Shared mailboxes for HR, and live chat for the product’s own support.

Built for Pakistan: CNIC, NTN, IBAN, EOBI and PESSI, FBR filer status, PKR and a July to June tax year are part of the data model, not custom fields.

Four surfaces, one API

The website, the HR web app, the Android app and a hidden operator console all talk to one NestJS API on PostgreSQL. Each company is a tenant, and the database itself enforces the wall between them.

Surfaces

  • WebsitePricing, docs, demo booking
  • HR web appAngular, with self service
  • Phone appFlutter, Android
  • Operator consoleUnlisted, its own sign-in
HRM APINestJS 12, one versioned contract

Behind the API

  • PostgreSQLRow-level security, forced
  • Mail serversSMTP, IMAP and POP3
  • PushEach company’s own Firebase
  • File storageSigned links, checked bytes
  • 01

    Wall one: the repository

    Every query goes through one repository that adds the tenant. Primary keys are the pair of tenant and id, so an id alone never finds a row.

  • 02

    Wall two: the database

    Row-level security is enabled and forced on every table. The app connects as a role that cannot bypass it, so a bug in wall one still returns nothing.

  • 03

    Sign-in

    Password plus an emailed code, or a passkey. Passwords hashed with scrypt; CNIC and bank numbers encrypted at rest.

Tested as if it were live

Nobody uses it yet, so the tests are the only users. Four suites, each one command, each on its own throw-away database. The numbers are from the latest recorded run.

  • Unit

    445 / 445

    Pure rules with no database: permissions, the payroll engine, mail parsing, settings access. About 25 seconds.

  • Tenant isolation

    16 / 16

    A second company aims 158 calls at the first one’s real ids: no leaks, no changed rows, no server errors. 116 tables audited for forced row-level security.

  • Scenarios and parity

    1,263 checks

    Every API scenario on a freshly seeded clone, including 614 checks that the API answers exactly like the web app’s mock.

  • Design system

    6 suites

    Playwright on desktop light, desktop dark and a phone, with axe for accessibility and visual capture.

The latest end-to-end run was 32 of 34. The two failures are expected: approval rules are being tightened so each step needs a user of that step’s role, and the old journeys still assume the looser rule.

Decisions and trade-offs

Fourteen are written down as decision records. These six shaped the product most.

  1. 01

    The mock is the contract

    The web app shipped first against an in-browser mock. The API now publishes which modules it serves; the app routes those to it and keeps the mock for the rest, and parity tests hold the API to the mock’s answers.

  2. 02

    Two walls between tenants

    A scoped repository could be enough until one query forgets it. Forcing row-level security in PostgreSQL costs some setup per connection and buys a second wall that code can’t skip.

  3. 03

    Records as documents

    Each record is stored as JSON in the shape the contract describes, with the fields that need indexes promoted to columns and a version for optimistic locking. Fast to evolve while the model still moves.

  4. 04

    One node, no Redis

    Rate limits, jobs and live chat run in one process on one PostgreSQL. It is the right size before launch, and the decision lists what scaling out needs: a shared store for limits and a pub/sub for chat.

  5. 05

    Books with one writer

    Accounting is double entry with a single function that posts: debits must equal credits, money is kept as decimal strings, and nothing is edited; a void posts a reversal.

  6. 06

    A console nobody can find

    The operators’ console sits on an unlisted path with its own sign-in, an authenticator code, short sessions and a lockout. It is kept out of search and out of every promo video.
