The life of a stake

Five steps across two portals. The investor signs every move from their own wallet; an admin funds rewards and approves each unstake on the chain it belongs to.

  1. 1Sign in with a wallet
  2. 2Stake on a chain
  3. 3Claim rewards
  4. 4Unstake and unbond
  5. 5Withdraw once approved
  • 01

    Sign in

    The wallet signs a one-time message and the API recovers the address from it, or Web3Auth signs the investor in with a social account.

  • 02

    Stake

    Coins go to the chain’s own staking contract. The portal switches the wallet to that network first.

  • 03

    Rewards

    An admin funds a chain’s rewards from the admin portal; investors claim them from My Assets.

  • 04

    Unbond

    An unstake waits the chain’s withdrawal days and an admin’s approval, then withdraw sends it back.

Permissions are transactions

Granting an admin a permission is a call to the AdminControl contract. The wallet asks, the row shows pending, and the switch flips only when the receipt arrives.

Decisions and what I’d change

Money on a chain, admins with different powers, and two portals built at once in eight weeks.

  1. 01

    The contract decides who is an admin

    Roles and the four permissions live in AdminControl. The API reads them at every sign-in and the database keeps only names and contacts, so a revoke on chain needs no second list to update.

  2. 02

    A signature, not a password

    The portal signs a one-time message and the API recovers the address from it. Nothing to store, reset or leak, and the wallet that signs in is the one that signs the transactions.

  3. 03

    Change the table after the receipt

    Every grant, chain update and approval waits for the transaction to be mined before the row changes, with a loading state per row and action, so one slow call never freezes the rest.

  4. 04

    Switch the network for the user

    Rewards and approvals run on the staking contract’s own chain. The portal asks the wallet to switch first and stops with a plain message if the user says no, instead of failing inside the wallet.

  5. 05

    Show the transaction, not a spinner

    Web3 Onboard connected the wallets, but its notifications were off, so a slow transaction was just a spinner. Today I’d show the hash, pending and confirmed with an explorer link, and keep the hash through a reload.

  6. 06

    One wallet stack, one pending state

    The admin portal used Web3 Onboard, the investor portal wagmi and Web3Auth: two ways to do one job. Today I’d pick one, and keep pending transactions in one hook instead of a boolean array per button.
