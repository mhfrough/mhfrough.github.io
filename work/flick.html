The real app

One page: who you are, a board for everyone nearby, the devices around you, and an inbox where nothing lands until you accept it. Captured from the live site with two real browsers.

On a phone

The same page in one column. Every device gets a random two-word name like Calm Heron, kept until you rename it, and shows up on the others with its kind and browser.

  • A device tile with Send files and Send text, and the transfer’s state under it
  • Offers wait with names and sizes; nothing downloads until you press Accept or Download
  • Received files stay in memory until you press Save

The two browsers met in a throwaway room: the public address lookup was answered with an address from the documentation range, so no real network appears anywhere. Flick never shows the address anyway.

How two browsers meet

Browsers cannot reach each other until something passes a few handshake messages. Flick has no server, so it borrows free public MQTT brokers and makes sure they only ever see noise. Step through it; the hashes and the ciphertext are computed live in your browser.

Step 1 of 6

Find the network

Each device asks api.ipify.org (or ipv4.icanhazip.com) for its public IPv4 address. Devices behind the same router get the same answer, so it becomes the meeting point.

An address from the documentation range. Try your own idea of one; nothing is sent.

  • Brisk Otter asks ipify203.0.113.24, same router
  • Room secretnetwork:203.0.113.24

Moving the bytes

Once the channel is open, Flick speaks its own small protocol: JSON for control, raw binary for file data. Files are always offered first and only sent once the receiver accepts.

Eight control messages

  • hello

    Name, device kind and label. Sent on open and again after a rename.

  • text

    Text or a link, straight into the inbox. Up to 100,000 characters.

  • offer

    File names, sizes and types, up to 500 files. Nothing moves yet.

  • reply

    Accept or decline. Only an accept starts the transfer.

  • file

    Marks which file the binary chunks that follow belong to.

  • got

    The receiver has every byte. Until then the sender shows the transfer as unfinished.

  • cancel

    Either side stops a transfer; both inboxes update.

  • unshare

    Takes a board item back off other devices, unless its files were already received.

Back-pressure, simulated

The sender reads the file 4 MB at a time and sends 64 KB pieces. When the channel’s buffer passes 8 MB it stops and waits for the browser’s “buffer low” event at 1 MB. Turn the wait off to see what it prevents.

Three ways to share

Like AirForShare for the room, like AirDrop for one device, and a link for everything else.

  • board

    Share with everyone

    Paste text or add files once and every device on the network gets them, including devices that open Flick later: a new device is handed the whole board as soon as it says hello. Drop files anywhere on the page and they go out at once.

  • tile

    Send to one device

    Tap a device, or drop files on its tile, and only that device is asked. Its owner sees names and sizes first and decides; the tile shows waiting, sending and done, with a cancel at every step.

  • #r=code

    A private link

    On guest Wi-Fi, a hotspot or another network entirely, Share a link opens a sheet with a QR code. The room code rides in the URL after #r=, so whoever opens it joins the same encrypted room from anywhere.

Engineering details

Small things that make a no-server tool hold up on real networks and real phones.

  • 01

    An MQTT client in about 110 lines

    MQTT 3.1.1 over WebSocket, QoS 0 only: connect, subscribe, publish, ping every 30 seconds, and a packet parser that copes with frames split across messages. Reconnects back off from 1 to 30 seconds.

  • 02

    Three brokers, one conversation

    Every message goes to EMQX, Mosquitto and HiveMQ at once. Each carries a random id inside its sealed body, and a rolling set of the last 2,000 ids drops the duplicates.

  • 03

    No glare

    When two devices hear each other, only the one with the lower id dials. The other answers with a direct hello so it is noticed, and ICE candidates that arrive before the offer are queued, not lost.

  • 04

    Memory that can page out

    Received chunks are folded into a Blob every 64 pieces, so the browser can move them out of memory. A file that grows past its announced size fails instead of filling the tab.

  • 05

    Awake while it works

    A screen wake lock is held only while a transfer runs, and a hidden tab shows unseen arrivals in its title, so a phone does not sleep halfway through a file.

  • 06

    Careful with what peers say

    Names, labels and file names from other devices are cleaned of control and direction-override characters and trimmed; slashes in file names are replaced. Shared links open with noopener and nofollow.

Decisions

Each one follows from the same constraint: a static page, no account, nothing stored.

  1. 01

    The public IP is the meeting point

    Devices behind one router share a public address, so Flick asks ipify (or icanhazip) for it and hashes it into a topic and a key. No codes to type, and brokers never see the address, only hashes of it.

  2. 02

    Borrowed brokers, sealed messages

    With no signalling server, free public MQTT brokers pass the handshake. Every message is AES-GCM encrypted in the page with a fresh 12-byte IV, so brokers see random bytes on a hashed topic.

  3. 03

    Offers before bytes

    Everyone behind the same public IP counts as nearby, which on a campus or office network can include strangers. So files are always offered first and never sent until the receiver accepts.

  4. 04

    Not Bluetooth

    Web Bluetooth can only connect to Bluetooth gadgets. It cannot advertise, so two browsers can never discover each other over it. Wi-Fi plus WebRTC is the path a web page actually has.

Limits, stated plainly

From the README, because a tool that moves your files should say where it stops.

Works

  • Phones and computers on the same Wi-Fi, in current Chrome, Edge, Firefox and Safari
  • Any network, through the private link and QR code
  • Many files at once, text and links, drag and drop, paste
  • Light and dark, following the system until you pick

Does not, by design

  • Transfers need both pages open; phones pause background tabs
  • Received files are held in memory until saved, so files of several GB suit a computer
  • Guest Wi-Fi, hotspots and client isolation keep devices apart; the link still works
  • About 1 in 10 setups, strict corporate NATs, block direct connections; that needs a TURN relay, which this build does not include
  • Public brokers have no uptime guarantee; three at once, and any MQTT-over-WebSocket broker can be added
